Статус: **NORMATIVE-DRAFT**  
Дата: 2026-07-26  
Исправление: названия уровней приведены к фактическому русскому интерфейсу
Codex Desktop пользователя.

## 1. Доступные уровни в текущем интерфейсе

В рабочем интерфейсе SceneLith доступны ровно пять уровней:

| Название в интерфейсе | Английское обозначение | Назначение |
|---|---|---|
| **Лёгкий** | Light / `low` | Быстрые и полностью определённые действия |
| **Средний** | Medium | Обычная работа с умеренным планированием |
| **Высокий** | High | Сложная многошаговая реализация и проверка |
| **Очень высокий** | Extra High / `xhigh` | Трудная архитектура, анализ нескольких tradeoffs и источников |
| **Ультра** | Ultra | Максимально глубокая составная работа с возможностью параллельной делегации |

`Max` отсутствует в текущем model picker и поэтому **не является рабочим
уровнем SceneLith**. Официальное руководство упоминает его как опциональный
уровень некоторых конфигураций, но прежняя рекомендация использовать `Max`
в интерфейсе пользователя была ошибочной.

## 2. Рациональный уровень прямо сейчас

Текущая стадия — не свободный разговор о возможностях, а создание канонической
архитектуры стандарта, сравнение prior art, поиск противоречий и запись решений,
которые затем определят bitstream и decoder.

> **Для текущей работы над стандартом SceneLith использовать «Ультра».**

Причины:

- ошибка в семантике state, reference safety или random access размножится по
  всей реализации;
- задача делится на независимые направления: prior art, bitstream, hardware,
  compression theory, failure analysis и conformance;
- полезно параллельно получать предложение и adversarial review;
- на этой стадии качество решения важнее экономии usage limit.

Если обсуждение является только быстрым brainstorming без принятия и записи
решения, достаточно **«Очень высокого»**. Перед переводом идеи в
`NORMATIVE-DRAFT` или `ACCEPTED` следует возвращаться на **«Ультра»**.

## 3. Где использовать каждый уровень

| Работа SceneLith | Рациональный уровень |
|---|---|
| Переименование, поиск строки, форматирование, обновление таблицы | **Лёгкий** |
| Сбор источников, обычная документация, запуск известных тестов | **Средний** |
| Реализация уже замороженного decoder tool, GPU kernel, test harness | **Высокий** |
| Проектирование одного сложного tool, RDO, debugging bit-exact ошибки | **Очень высокий** |
| Архитектура всего стандарта, bitstream/state freeze, полный design review, CfP integration | **Ультра** |

## 4. Разница между «Очень высоким» и «Ультра»

**Очень высокий** рационален, когда существует одна трудная, но достаточно
цельная задача: вывести state transition, спроектировать entropy tool,
разобрать regression или написать сложный модуль.

**Ультра** рациональна, когда один результат требует нескольких разных ролей:
архитектора, исследователя prior art, аппаратного рецензента, автора
спецификации и критика. В этом режиме Codex может инициативно распараллеливать
подходящие части работы.

Следовательно, «Ультра» — не просто обязательная настройка для каждого
действия. Её преимущество раскрывается на составных задачах.

## 5. Рабочая схема проекта

1. **Архитектурные сессии и решения стандарта — Ультра.**
2. **Изолированные сложные исследования и алгоритмы — Очень высокий.**
3. **Основная реализация по готовой спецификации — Высокий.**
4. **Механические проверки и документация — Средний.**
5. **Тривиальные локальные изменения — Лёгкий.**

Для root-задачи на уровне **«Ультра»** подзадачам назначается минимальный
достаточный уровень. Это сохраняет максимальное качество координации, не
расходуя самый дорогой режим на boilerplate.

## 6. Связь со сроком первой версии

Срок 6–12 недель предполагает:

- **Ультра** на архитектурных развилках и интеграции;
- **Очень высокий** на новых compression hypotheses и тяжёлом debugging;
- **Высокий** на реализации;
- **Средний/Лёгкий** на массовых механически проверяемых задачах;
- автоматические GPU/CI workers, работающие независимо от model inference.

Дополнительное reasoning не сокращает физическое время компиляции, обучения и
benchmark runs. Оно сокращает число дорогих неверных веток и повторных
реализаций.

## 7. Официальная основа

OpenAI рекомендует выбирать минимальный уровень, который даёт требуемое
качество. High и Extra High предназначены для трудной работы с несколькими
шагами, источниками и tradeoffs. Ultra использует максимальное reasoning и
может разделять сложную работу между субагентами.
